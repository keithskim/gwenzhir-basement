| Name | Hex |

**Typography**

Single typeface: Pretendard 600, loaded via CDN. Named token: Base Text.

Six font sizes (XS–2XL) with paired line heights. Line height formula: `font-size + 0.5rem`, giving a constant absolute 0.5rem of leading above the cap height at every size. All values in rem.

| Step | Size | Line height |
|---|---|---|
| XS | 0.75rem | 1.25rem |
| S | 1rem | 1.5rem |
| M | 1.5rem | 2rem |
| L | 2.25rem | 2.75rem |
| XL | 3rem | 3.5rem |
| 2XL | 4rem | 4.5rem |

**Border radius**

Three steps: S (0.25rem, default), M (0.5rem), L (1rem). Border color section shows light and dark contexts. Divider shown inside a bordered box to distinguish it from a live page divider.

**Spacing**

Five steps, strict 2× multiplier: XS–XL (0.5 / 1 / 2 / 4 / 8rem). Visualized as bottom-aligned rising bars with S border radius.

**Sizes**

Five steps, strict 2× multiplier: XS–XL (1 / 2 / 4 / 8 / 16rem). Visualized as bottom-aligned squares.

### Design conventions settled

- All units in rem throughout the document
- No all-caps or non-standard letter-spacing in UI labels
- Sample texts are bilingual Korean/English
- The document applies its own tokens to itself — font sizes, line heights, spacing, and border styles all reference CSS custom properties

---

## Decisions and rationale

**Why a constant 0.5rem leading gap?**
Tying line height to font size by a fixed absolute amount means large text stays tight while small text has proportionally more breathing room. The relationship is simple enough to calculate in your head.

**Why 2× spacing and size multipliers?**
Clean ratios make it easy to step between scales without ambiguity. The jumps are large enough to be visually distinct and deliberate rather than incremental.

**Why Pretendard?**
Good Korean/Latin mixed-script support in a single weight. 600 reads well across a wide range of sizes without needing separate weights for hierarchy — hierarchy comes from size instead.

**Why a flat grayscale palette to start?**
Establishing the neutral foundation before introducing hue. Every UI needs a complete grayscale; color is additive from here.

## Session 2

Continued building the Basement UI reference page. Expanded colors, added full typography and scheme sections, and refined layout and interactions.

### What changed

**Reference page — layout**

Added a sticky sidebar with section navigation (Colors, Typography, Borders, Spacing, Sizes). Selecting a section hides all others and shows only the active one. Subsections are separated with horizontal rules that sit under the subsection heading. Sample content is wrapped in bordered, padded `.sample-box` containers. All section and subsection headings are semantic HTML (h2/h3/h4) with a UA style reset so they inherit design-system size and weight rather than browser defaults.

**Colors — Palette**

Added three hue groups alongside the grayscale row: Red, Green, Blue. Each hue has three shades: Dark (for backgrounds on dark themes / strong fills), Mid (primary accent), Light (tinted background on white). Final values:

| Hue | Dark | Mid | Light |
|---|---|---|---|
| Red | `#8B0000` | `#EE3333` | `#FFE8E8` |
| Green | `#1A5C28` | `#33BB55` | `#E0F8E8` |
| Blue | `#1A2E6E` | `#3366EE` | `#E0EAFF` |

Swatches use a wide 4:1 aspect ratio chip. White and light-tinted swatches get a `#DDDDDD` border so they read against the white page background.

**Colors — Scheme**

Scheme section assigns colors to six semantic roles organized into three groups: Background (Primary, Secondary), Text (Primary, Secondary), Border (Resting, Highlighted). Each role has two independently assignable slots: Light theme and Dark theme. The scheme-list shows column headers "Light" / "Dark". Clicking either slot opens a picker populated from the full 14-color palette; selecting a chip updates that slot's swatch and closes the picker.

Default assignments:

| Role | Light | Dark |
|---|---|---|
| Background Primary | White | Black |
| Background Secondary | Light Gray | Dark Gray |
| Text Primary | Black | White |
| Text Secondary | Gray | Light Gray |
| Border Resting | Light Gray | Dark Gray |
| Border Highlighted | Black | White |

**Typography**

Seven subsections: Typeface, Sizes, Headings, Body, Caption, Links. Each uses `.sample-box` wrappers with divider borders between entries.

- Typeface shows a bilingual display-size sample first, then the font-meta (name, weight).
- Sizes shows all six steps with varying vertical padding (XS/S rows tight, XL/2XL rows relaxed) and gray sample text that scales with each step.
- Headings defines H1–H4 with tight letter-spacing on larger sizes.
- Body defines paragraph (S, Dark Gray, max 40rem), blockquote (left border, same size).
- Caption defines XS, Gray.
- Links: underline with `text-underline-offset: 0.2em` and `text-decoration-thickness: 1px`; props shown below the sample box in natural language (not hyphenated variable names).

**CSS rules of note**

- `h1,h2,h3,h4,h5,h6 { font-weight: inherit; font-size: inherit; }` — prevents browser defaults from overriding design-system tokens on semantic heading elements.
- `.subsection-label:has(+ .sample-box) { border-bottom: none; padding-bottom: 0; }` — suppresses the horizontal rule under a subsection heading when the sample box immediately follows (border-bottom would double with the box's own top border).
- `.border-group + .border-group { margin-top: var(--spacing-l); }` — 4rem vertical gap between subsections.
- `.scheme-group + .scheme-group { margin-top: var(--spacing-m); }` — 2rem vertical gap between scheme role groups.

### Decisions and rationale

**Why `:has()` for the conditional subsection border?**
There is no CSS "previous sibling" selector, so the only pure-CSS solution is `:has(+ .sample-box)` on the heading. It is widely supported in modern browsers (Chrome 105+, Safari 15.4+, Firefox 121+) and keeps the HTML free of modifier classes.

**Why one picker per scheme row rather than two?**
Having two open pickers per row would create ambiguous stacking. One picker per row, opened by the last-clicked button (`activeBtn` tracker), always appears in the same place and clearly targets one slot at a time.

**Why Green instead of Yellow?**
Yellow is difficult to make both visually vibrant and accessible. Green provides similar warmth-contrast utility with better legibility and a wider usable shade range.

### Decisions and rationale

**Why Phosphor?**
Regular-weight stroke icons pair well with Pretendard 600. Phosphor has broad UI coverage, MIT license, and a web-font delivery that fits the zero-build-step reference page. Regular weight only is vendored to keep the asset small.

**Why 7 / 9 / 11 / 13 page columns?**
Sidebar holds 2 columns at every viewport; content gets the remainder (5 / 7 / 9 / 11). Odd totals keep a clear center column on the full-page grid while giving content more room than the earlier 3 / 5 / 7 / 9 scale.

**Why vendoring instead of CDN?**
The reference page is a single HTML file meant to work offline and stay pinned to a known icon version. `package.json` tracks the npm version; font files live in `vendor/` for Dropbox sync without relying on `node_modules`.

- Tag and Avatar gained **Sizes** subsections with centered sample boxes
- Removed redundant meta detail props; labels only (e.g. Default, With label, S / M / L)

**Sample list layout (Foundation + Components)**

- Equal sample-box height in a shared row via subgrid row tracks on `.type-sample-list`
- Box-to-meta spacing uses `row-gap: var(--spacing-xs)` on `.type-sample-item`, matching icon swatch and token-name spacing
- Component sample boxes use `padding-block: var(--spacing-s)` by default

**Icons**

- Expanded catalog to ~100 icons in four groups; icon-group spacing increased to `--spacing-m`
- Catalog cells use `icon-face--l`; column snap unchanged (span 2 below wide, span 1 at wide+)

**Dropdown**

- Triggers updated to `btn--default`; interactive open/close JS retained

### Decisions and rationale

**Why subgrid row tracks for equal box height?**
Per-item `1fr` rows sized independently and failed for Checkbox-style rows where label length varies. Sharing row 1 across items in the same list row forces all sample boxes to the tallest neighbor.

**Why breakpoint-controlled flex-direction on button type rows?**
`flex-wrap` caused bordered Default/Accent buttons to stack while narrower Ghost buttons stayed horizontal in the same viewport. A single media-query flip keeps all three type demos in sync.

**Why strip meta detail columns from Components?**
Foundation swatches and icon cells already use a single label line. Extra prop columns added noise without helping scan the live reference.
